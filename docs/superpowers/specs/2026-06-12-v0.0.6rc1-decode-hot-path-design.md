# v0.0.6rc1 Decode Hot Path Design

## Goal

Reduce per-token control, communication, and detokenization overhead without
changing Qwen3 generation semantics or the existing PagedAttention/NPU Graph
execution model.

## Scope

1. Qwen3, Qwen3 MoE, and Qwen3-VL return vocabulary-sharded logits in TP mode.
2. A shared sampler performs exact distributed greedy selection and distributed
   candidate Top-P sampling, with an exact full-vocabulary fallback when the
   candidate set cannot prove that it contains the nucleus.
3. Continuous batching retains sampled tokens and decode positions on the
   device. Rank 0 performs one batched D2H token transfer per model step for
   streaming; worker ranks perform none.
4. Streaming detokenization decodes a bounded suffix and falls back to full
   decoding only when the suffix cannot be reconciled safely.
5. Continuous-batching TP commands use tensor broadcasts. Legacy single-request
   and multimodal request setup may continue using object broadcasts because
   they are not issued once per decode token.

## Architecture

### Vocabulary-parallel sampling

`lite_llama/sampling.py` owns sampling for all text generation paths.

- Non-TP models use local greedy or Top-P sampling.
- TP greedy sampling exchanges only each rank's local maximum and global token
  ID.
- TP stochastic sampling exchanges bounded top candidates and the exact global
  softmax normalization. If the selected nucleus boundary is not above all
  excluded candidates, the sampler falls back to gathering full logits. This
  preserves correctness rather than silently approximating Top-P.
- Rank 0 performs multinomial sampling and broadcasts only the resulting token.

### Device-resident decode state

`ContinuousBatchModelBackend` stores the latest sampled token and next position
for every active model request as device tensors. Decode input tensors are
assembled from those tensors instead of reconstructing them from Python token
lists. Rank 0 copies the final sampled batch to Host once because HTTP streaming
requires token IDs on the CPU.

### Incremental detokenization

Each `BatchRequest` owns an incremental decoder. It compares the decoded text of
a bounded token suffix before and after appending the new token. If the suffix
is stable, only the new text is emitted. If token-boundary behavior changes the
suffix, it falls back to decoding the complete generated sequence.

### Tensor TP control plane

The server broadcasts a fixed header followed by integer and floating-point
payload tensors. Prefill includes request metadata and flattened prompt tokens;
decode and release include only stable numeric request IDs. Worker-side request
and device state persist across steps.

## Compatibility and fallback

- Single-card behavior remains unchanged.
- Exact stochastic output is prioritized over avoiding all full-logit gathers.
- NPU Graph captures vocabulary-sharded model output and sampling remains
  outside the graph.
- Existing `.pth` checkpoints remain compatible.
- No scheduler policy, chunked prefill, prefix caching, or multi-node behavior
  is added in this release.

## Verification

- CPU unit tests cover local sampling, simulated TP greedy selection, candidate
  nucleus correctness/fallback decisions, incremental detokenization, device
  state reuse, and tensor command serialization.
- Existing continuous batching and server usage tests remain green.
- Static compilation and diff checks run locally.
- Atlas validation must compare deterministic output and benchmark TP2 with
  Graph on/off.
