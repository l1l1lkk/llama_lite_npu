# v0.0.8rc6 Release Report

Date: 2026-06-22

## Scope

`v0.0.8rc6` is a correctness release for continuous-batching context-length handling. It does not change model kernels or claim a new performance result.

## Problem

A chunked-prefill / continuous-batching request could crash a TP worker during decode:

```text
RuntimeError: Paged KV allocation failed for request 3: current_tokens=1024, max_seq_len=1024, free_pages=10331
```

The important signal is `current_tokens == max_seq_len` while `free_pages` is still large. This means HBM pages were available, but the request had reached the per-request context limit.

## Root cause

The scheduler accepted requests where:

```text
prompt_tokens + requested_generation_tokens > max_seq_len
```

Then decode attempted to append another KV token after the request had already reached `max_seq_len`. In TP mode, the worker rank hit the Paged KV extension failure and terminated the distributed process.

This was not an NPU Graph problem and not a TP `control_id` synchronization problem. The failing layer was request admission / decode-boundary validation.

## Changes

- `ContinuousBatchScheduler.submit(...)` now rejects prompts at or beyond context capacity.
- `ContinuousBatchScheduler.submit(...)` now rejects `prompt_tokens + max_new_tokens > max_context_tokens`.
- `ContinuousBatchScheduler.step(...)` now finishes active requests with `length` before backend decode if their context is already full.
- `ContinuousBatchModelBackend` exposes `max_context_tokens` from `ModelExecutor.max_seq_len`.
- `_TpCoordinatedContinuousBackend` forwards `max_context_tokens` from its local backend.
- `server.py` maps context-capacity submission failures to HTTP 400.

## Validation

Local validation:

```bash
git diff --check
python -m py_compile lite_llama/continuous_batching.py server.py
python -m unittest tests.test_continuous_batching tests.test_server_batching tests.test_tp_control -v
```

All tests passed in the development environment.

## Operational note

For EvalScope runs with random prompts, `--max_seq_len` must cover the tokenizer/chat-template-expanded prompt plus requested output tokens. For example, if testing prompts up to roughly 1024 tokens and `--max-tokens 128`, start the server with at least:

```bash
--max_seq_len 1536
```

`--max_seq_len 2048` is safer for chat-template overhead and tokenization variance.
