# v0.0.13rc1 发布记录

## 版本定位

v0.0.13rc1 对应本阶段的 P0 / P1：

- P0：补齐合并主分支前的稳定性验证入口。
- P1：继续推进调度器工程化，让连续批处理在混合 prefill / decode 压力下更稳定。

本版本不引入新模型，不改变权重格式，也不改变 Dense / MoE 的模型结构。

## 问题

连续批处理进入可用阶段后，新的主要问题不是单个算子是否能跑，而是服务端调度是否稳定：

- 正在 decode 的流式请求容易被新请求 prefill 插入同一个调度 tick；
- prefill 会占用计算和通信窗口，导致已有请求的 ITL 和 P99 抖动；
- 合并主分支前缺少一条固定验证命令，容易遗漏文档版本、编码、单测和编译检查。

## 优化思路

推理服务通常应该优先保证已经开始输出的请求稳定继续输出。原因是：

- 用户对已经开始流式返回的卡顿更敏感；
- decode 是交互体验中的核心路径；
- 新请求的 TTFT 可以接受轻微排队，但老请求的 ITL 抖动会直接表现为“回复一卡一卡的”。

因此本版本采用更保守的 decode-first 策略：

```text
如果当前 tick 有 active decode：
  先 decode
  不在同一个 tick 里接纳新的 prefill
否则：
  按原 token budget / chunked policy 接纳 prefill
```

## 解决方案

### Decode Priority

新增服务端参数：

```bash
--decode_priority
--no_decode_priority
```

默认开启 `--decode_priority`。

开启后：

- active decode 存在时，新 prefill admission 延后到下一 tick；
- chunked prefill 的后续 chunk 也会在 active decode 存在时延后；
- 已经 active 的 decode 仍受 `--max_decode_tokens` 控制；
- 关闭开关后可恢复旧行为，方便做 A/B 测试。

### Release Validation

新增：

```bash
python scripts/validate_release.py
```

该脚本会执行：

- Markdown UTF-8 replacement 字符检查；
- `VERSION` 与 release 文档、README 同步检查；
- 全量单元测试；
- `lite_llama` 和 `server.py` 编译检查；
- `git diff --check` 空白检查。

## 验证

本地验证命令：

```bash
python scripts/validate_release.py
python -m unittest tests.test_continuous_batching tests.test_server_batching -v
```

服务器验证建议：

```bash
ASCEND_RT_VISIBLE_DEVICES=6,7 \
python -m torch.distributed.run --nproc_per_node=2 server.py \
  --checkpoints_dir /data/liuke/llama_lite_npu/my_weight/Qwen3-32B/ \
  --host 0.0.0.0 \
  --port 8213 \
  --max_seq_len 4096 \
  --page_size 16 \
  --compiled_model \
  --continuous_batching \
  --decode_priority \
  --max_batch_size 32 \
  --sampling_candidate_k 2048
```

对比测试时可以用 `--no_decode_priority` 重启服务，然后复用相同 EvalScope 命令对比：

- Output Throughput；
- TTFT；
- TPOT；
- ITL；
- P95/P99 Latency；
- `/metrics` 中 queue wait 和 inter-token latency 分布。
