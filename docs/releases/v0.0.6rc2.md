# Lite Llama NPU v0.0.6rc2

- 发布日期：2026-06-12
- 变更类型：性能回归修复
- 对比版本：v0.0.6rc1

## 问题

v0.0.6rc1在Qwen3-32B、TP=2、Batch=4、Decode NPU Graph场景下，Greedy吞吐为
19.7 tok/s；v0.0.5rc2相同配置为21.3 tok/s，回归约7.5%。

首版Vocab Parallel Greedy虽然降低了通信字节数，但对Batch中的每一行分别交换最大
Logit和Token ID。Batch=4时每个Decode Step产生八次小AllGather，HCCL启动延迟超过了
通信量降低带来的收益。

## 修复

新路径对整个Batch一次性执行：

```text
local logits [batch, local_vocab]
  -> row-wise max value / local token id
  -> global token id
  -> pack float32 [batch, 2]
  -> one AllGather
  -> global winner per batch row
```

Qwen3词表ID远小于float32可精确表示整数的上限`2^24`，因此打包Token ID不会损失
整数精度。相同Logit的Tie仍按Rank和分片内较小Token ID优先，与完整词表Argmax一致。

## 参数显示

Benchmark仍保留`--top_p`默认值，但现在根据Temperature显示实际状态：

```text
Temperature: 0.0
Top-p:       inactive (temperature=0)
```

当`temperature > 0`时继续显示实际Top-P值。

## 验证

本地测试验证：

- Batch=2跨Rank Greedy结果正确；
- 整个Batch只调用一次候选Collective；
- Greedy与Top-P状态显示正确；
- 既有采样、Continuous Batching、Server、NPU Graph和MoE测试无回归；
- Python静态编译通过。

Atlas复测应使用与v0.0.5rc2和v0.0.6rc1完全相同的命令，并确认：

```text
Temperature: 0.0
Top-p: inactive
Graph captured > 0
Graph replays > 0
Graph fallbacks = 0
```

## Atlas实测结果

共同配置：Qwen3-32B、FP16、TP=2、Batch=4、Prompt约128 tokens、生成256 tokens、
Decode NPU Graph成功Replay。

| 版本与采样策略 | Avg throughput | Batch throughput | 单Token耗时 | 平均时间 |
|---|---:|---:|---:|---:|
| v0.0.5rc2 Greedy，temperature=0 | 21.3 tok/s | 85.0 tok/s | 47.04ms | 12.043s |
| v0.0.6rc1 Greedy，temperature=0 | 19.7 tok/s | 78.6 tok/s | 50.87ms | 13.023s |
| v0.0.6rc2 Greedy，temperature=0 | 22.1 tok/s | 88.6 tok/s | 45.16ms | 11.560s |
| v0.0.6rc1 Top-P，temperature=0.6、top_p=0.9 | 17.7 tok/s | 70.9 tok/s | 56.41ms | 14.441s |
| v0.0.6rc2 Top-P，temperature=0.6、top_p=0.9 | 17.9 tok/s | 71.7 tok/s | 55.83ms | 14.293s |

Graph统计均为`attempts=3`、`captured=3`、`replays=1785`、`fallbacks=0`。

## 结论

- Greedy相对v0.0.6rc1提升约12.2%，说明Batch级单Collective修复有效；
- Greedy相对v0.0.5rc2提升约3.8%，说明Vocab Parallel Greedy在当前双卡Batch=4下
  只有小幅净收益；
- Top-P相对v0.0.6rc1只提升约1.1%，基本没有被本次修复触及；
- 当前未出现Graph回退，性能差异来自采样与通信路径本身。

收益没有显著放大的原因是：旧版完整Logits AllGather虽然通信量大，但处于Graph内且
调用次数少；新版降低通信字节数后，局部Argmax、候选打包和小规模AllGather仍在Graph外。
在双卡低Batch场景下，采样通信不是唯一瓶颈，Transformer层MatMul、Attention和HCCL
AllReduce仍占主要时间。后续要继续优化Top-P，需要先把Top-K候选、概率归一化和采样
向量化，或进一步尝试把Greedy采样纳入Graph/自定义算子边界。
