# v0.0.7rc2 Release Notes

Date: 2026-06-17

## Summary

v0.0.7rc2 fixes an idle-time TP continuous-batching failure on Ascend. The previous implementation used HCCL tensor broadcast as the control-message queue between rank 0 and worker ranks. When the server stayed idle, rank 1 could block inside a long-lived NPU/HCCL receive path and hit Ascend runtime watchdog timeout `507048`.

## Root cause

The failing stack was:

```text
rank1 -> _tp_continuous_worker_loop
      -> TensorCommandChannel.receive
      -> header.cpu().tolist()
      -> ACL stream synchronize failed, error code: 507048
```

`header.cpu().tolist()` was only the synchronization point that surfaced the failure. The root problem was using an NPU/HCCL collective as a long-idle command queue.

## Fix

- Added `StoreCommandChannel`, a CPU-side command channel backed by `torch.distributed.TCPStore`.
- Continuous-batching TP control messages now use CPU store metadata instead of HCCL tensor broadcast.
- Worker ranks block on CPU `store.get()` while idle and enter NPU/HCCL only for actual model work.
- Kept the old `TensorCommandChannel` implementation for compatibility/tests, but server continuous batching no longer uses it.
- Added CPU serialization helpers: `encode_store_payload` and `decode_store_payload`.

## Operational notes

`StoreCommandChannel` uses:

- `MASTER_ADDR` from torchrun.
- `LITE_LLAMA_TP_STORE_PORT` if set, otherwise `MASTER_PORT + 2000`.
- `LITE_LLAMA_TP_STORE_TIMEOUT` if set, otherwise 7200 seconds.

If another process occupies the derived TCPStore port, set a free port explicitly:

```bash
export LITE_LLAMA_TP_STORE_PORT=31607
```

## Verification

- Unit tests cover CPU store serialization and fake-store send/receive.
- Server contract tests verify continuous batching uses `StoreCommandChannel` and not `TensorCommandChannel`.
- This release should be validated on Atlas by starting TP server, leaving it idle longer than the previous failure window, then running `/health` and a real inference request.

## Known limitations

- `/health` still primarily reflects rank 0 HTTP availability. A full multi-rank health protocol is still a future improvement.
- Legacy non-continuous TP paths still use object broadcast and are not changed in this bugfix.
