# Lite Llama NPU v0.0.5rc3

- 发布日期：2026-06-12
- 变更类型：文档、实测状态与使用方式同步
- 代码执行逻辑：相对v0.0.5rc2无变化

## 本次同步

### README能力矩阵

README现在明确区分：

- Qwen3 Dense、Qwen3 MoE、Qwen3-VL和历史模型路径；
- Tensor Parallel与单机Expert Parallel；
- 文本Continuous Batching与视觉模型请求级路径；
- Dense/MoE TP Graph和MoE EP Eager的支持边界；
- 当前仅支持单机多卡，尚未支持多机TP × EP。

### MoE启动方式

Qwen3-30B-A3B拆分为两条推荐命令：

```text
TP + compiled_model -> 可尝试Decode NPU Graph
EP + no_compiled_model -> 固定使用Eager
```

同时补充`LITE_LLAMA_MOE_BACKEND=auto|eager|gmm|routed_gemv`选择规则，以及
Continuous Batching对PagedAttention的依赖。

### EP性能记录

补录v0.0.5rc2双卡Atlas 910B3结果：

| 配置 | 结果 |
|---|---:|
| 模型 | Qwen3-30B-A3B FP16 |
| 并行 | EP=2 |
| Batch / Prompt / Output | 4 / 约128 / 256 |
| NPU Graph | 关闭 |
| 平均生成时间 | 46.359s |
| Avg throughput | 5.5 tok/s |
| Batch throughput | 22.1 tok/s |
| 单Token耗时 | 181.09ms |

该结果比旧MoE TP Eager基线约高10%，但现有数据没有锁定同一版本和同一后端，不能把差异
全部归因于EP。

### Profiler与通信分析

README中的Profiler示例改为MoE EP Eager采集，并要求增加TP Eager对照。后续重点观察：

- HCCL AllReduce总耗时和Rank等待差异；
- 通信与AI Core计算重叠率；
- EP专家assignment负载倾斜；
- Routed-GEMV与GMM在不同Batch下的分界点。

## 当前已知架构限制

- EP仍使用“本地专家计算 + 输出AllReduce”，不是Token All-to-All；
- EP动态本地assignment依赖`torch.nonzero`，因此自动禁用Decode NPU Graph；
- TP/EP复用单一全局进程组，尚未实现二维Process Mesh；
- 分布式设备映射使用全局Rank，当前只适合单机多卡；
- 通信操作为同步AllReduce/AllGather，尚未实现计算通信重叠；
- Continuous Batching尚无Chunked Prefill、抢占和优先级。
