# Lite Llama NPU v0.0.5rc2

- 发布日期：2026-06-12
- 变更类型：Qwen3 MoE Expert Parallel兼容性修复

## 问题

`v0.0.5rc1`使用以下组合时：

```text
model=qwen3_moe
moe_parallel_mode=ep
compiled_model=true
```

Decode Graph Capture进入EP本地专家路由中的`torch.nonzero`，CANN报告：

```text
call aclnnNonzero failed, error code is 107027
Not allow to synchronize captured-stream
```

这不是权重布局或EP数值错误。`aclnnNonzero`需要同步stream，而NPU Graph禁止同步正在
Capture的stream。该底层错误会污染Capture stream，普通异常捕获后的Eager fallback
不能保证进程继续运行。

## 修复

Graph能力判断增加MoE并行模式：

```text
Qwen3 MoE + TP -> 允许尝试Decode Graph
Qwen3 MoE + EP -> 启动时禁用Decode Graph
Dense模型      -> 保持原Graph策略
```

EP仍然保留本地assignment压缩、Routed-GEMV/GMM和专家输出AllReduce，只将Decode执行
保持在Eager模式。

## 测试命令

```bash
ASCEND_RT_VISIBLE_DEVICES=6,7 \
python -m torch.distributed.run --nproc_per_node=2 \
  examples/benchmark_tp.py \
  --checkpoints_dir /data/liuke/llama_lite_npu/my_weight/Qwen3-30B-A3B/ \
  --batch_size 4 \
  --prompt_len 128 \
  --max_gen_len 256 \
  --page_size 16 \
  --moe_parallel_mode ep \
  --compiled_model \
  --warmup 2 \
  --iterations 5
```

即使保留`--compiled_model`，启动日志也应出现：

```text
NPU Graph is unavailable for model_type=qwen3_moe moe_parallel_mode=ep;
using eager decode.
```

且不应再出现`aclnnNonzero` Capture错误。

如需验证MoE NPU Graph，应改用：

```text
--moe_parallel_mode tp --compiled_model
```

## 已知限制

EP动态压缩本地专家assignment会产生动态中间Shape。恢复EP Decode Graph需要用固定容量
dispatch buffer和有效位mask替代`torch.nonzero`，不能简单重新开放Capture。

## Atlas 910B3验证结果

双卡EP Eager已经完成实测：

```text
Model: Qwen3-30B-A3B FP16
Hardware: 2 × Atlas 910B3
Parallel: EP=2
Batch: 4
Prompt: 约128 tokens
Output: 256 tokens
NPU Graph: off
Warmup / Iterations: 2 / 5
```

| 指标 | 结果 |
|---|---:|
| 平均生成时间 | 46.359s |
| Avg throughput | 5.5 tok/s |
| Batch throughput | 22.1 tok/s |
| 单Token耗时 | 181.09ms |

该结果证明EP Eager路径能够完成正式Benchmark。相对旧MoE TP Eager基线的5.0 tok/s约提升
10%，但测试版本和`auto`后端解析状态并非完全相同，因此不能将全部差异归因于EP。
