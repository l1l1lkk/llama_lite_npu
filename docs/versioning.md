# 版本管理与发布规范

本项目从 `0.0.1rc1` 开始使用统一版本号、Git Tag、变更日志和版本开发报告。

## 版本格式

代码版本采用兼容 PEP 440 的格式：

```text
MAJOR.MINOR.PATCHrcN
```

当前快速开发阶段主要使用：

```text
0.0.XrcN
```

Git Tag 在版本号前增加 `v`：

```text
v0.0.1rc1
```

仓库根目录的 [`VERSION`](../VERSION) 是当前版本的唯一文本标识。

## 升级规则

### 功能大更新

只有影响面较大的功能更新才提升基础版本号，并从 `rc1` 开始。若紧邻的基础版本号已经存在或被占用，使用下一个未使用的版本号：

```text
0.0.12rcN -> 0.0.14rc1  # 0.0.13 已存在时
```

典型场景：

- 新增模型架构、量化体系或新的分布式并行模式；
- 引入 Continuous Batching、Vocab Parallel Sampling 等影响主要推理链路的大能力；
- 大规模改变执行引擎、调度架构或算子体系。

### 小功能或 Bug 修复

范围较小、保持整体架构不变的公开功能，以及影响正确性、稳定性、兼容性、部署或性能回退的 Bug 修复，只增加 RC 编号：

```text
0.0.1rc1 -> 0.0.1rc2
```

例如，在既有 Continuous Batching 采样链路中增加 `min_tokens` 请求字段与逐行 EOS mask，属于小功能：

```text
0.0.13rc2 -> 0.0.13rc3
```

只有需要用户重新部署或影响运行结果的 Bug 修复才触发版本升级。错别字、注释和纯文档修订不触发版本升级。

### 不升级版本

以下变更默认不升级版本号，也不创建独立版本报告：

- 新增或调整 benchmark 数据与测试脚本；
- 测试报告、文档、注释和示例命令修订；
- CI、格式化和不改变运行逻辑的工程维护；
- 不影响公开接口、正确性和性能的小型内部整理。

如果一次提交同时包含多类变更，按影响最大的类别确定版本：

```text
功能大更新 > 小功能或 Bug 修复 > 测试/文档/工程维护
```

## 每次发布必须更新

触发版本升级时，必须同步完成：

1. 更新根目录 `VERSION`；
2. 在 `CHANGELOG.md` 顶部增加倒序版本记录；
3. 新建 `docs/releases/v<版本号>.md`；
4. 版本报告记录相对上一版本的功能、修复、性能、测试环境、验证方法和已知限制；
5. README只展示最新版本、最新性能以及相对vLLM-Ascend基座的对比；
6. README链接到最新版本报告、完整CHANGELOG和本规范；
7. 创建并推送对应Git Tag，例如`v0.0.2rc1`。

## 自动执行约定

后续修改代码时，应先按本规范判断是否触发发版：

- 触发发版：自动计算新版本号并更新上述全部文件；
- 不触发发版：只提交功能、测试或文档改动，不修改版本号；
- 无法判断影响级别时，在提交前明确说明判断依据。

## 稳定版本

当接口、正确性和性能测试流程趋于稳定后，发布首个稳定里程碑：

```text
0.1.0
```

稳定版本之后再逐步采用更完整的语义化版本策略。
